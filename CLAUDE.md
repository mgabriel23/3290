# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A mobile-first 2D space shooter built with vanilla JavaScript (native ES modules) and the Canvas 2D API. No frameworks, no bundler, no `package.json` — plain static files served via XAMPP (the project lives in `htdocs/`, served at `http://localhost/space-shooter/`).

## Current state

A complete core gameplay loop, past the "foundation" stage this file used to describe. The flow: [Game.js](js/core/Game.js) boots into [PrologueScene.js](js/scenes/PrologueScene.js) (a beat-by-beat opening cinematic ending on a title card + PLAY button) → [TutorialScene.js](js/scenes/TutorialScene.js) (five hints pointing at the real HUD/barrier UI, dismissed by tap/swipe) → [GameplayScene.js](js/scenes/GameplayScene.js), which composes the player ship, a wave/level system, and the barrier the player defends.

Combat: the player auto-fires straight up ([Bullets.js](js/entities/Bullets.js)) against a roster of enemy types spawned by [WaveManager.js](js/entities/WaveManager.js) per `Config.waves.levels`:
- **Scout / Rocketeer** ([Enemy.js](js/entities/Enemy.js)) — enter, park, fire aimed bullets or homing rockets ([Rockets.js](js/entities/Rockets.js)) on a reload cycle.
- **Sniper** ([SniperEnemy.js](js/entities/SniperEnemy.js)) — same hull, but charges then fires a real bullet ([SniperBullets.js](js/entities/SniperBullets.js)) at the player's *current* position, with a "!" warning telegraph; the bullet itself crawls at launch before rocketing up to full speed.
- **Drifter family** ([DrifterEnemy.js](js/entities/DrifterEnemy.js)) — four path variants (looping drifter, sweeping rows, diving wedge, sine-sway weaver) sharing one tentacle-creature body, each formation flying a shared precomputed path; they lash a slow tracking projectile ([DrifterProjectiles.js](js/entities/DrifterProjectiles.js)) at the player.
- **Bouncer family** ([BouncerEnemy.js](js/entities/BouncerEnemy.js)) — wireframe hexagons that bounce off walls/barrier under constant gravity; variants split into fragments on death or carry an absorbing shield.

Death effects are pooled shockwave-rings + sparks ([Particles.js](js/entities/Particles.js)); the barrier ([Barrier.js](js/entities/Barrier.js)) takes damage from bounces and pulses on impact; [HUD.js](js/entities/HUD.js) draws the score/gold panels (currently static placeholders — no scoring system is wired up yet, deliberately).

[IntroScene.js](js/scenes/IntroScene.js) (a "swipe up to continue" prompt, the game's original entry point) still exists and works, but `Game`'s constructor currently boots straight into `PrologueScene` with `devSkipToTitle: true` as a dev convenience — see the comment right above that line for the one-line change that restores the full Intro → Prologue flow. Don't treat IntroScene as dead code and remove it.

[preview.html](preview.html) is a separate, self-contained design sandbox for sketching new enemy/boss hulls before they're wired into real entity classes (see its own header comment) — it is **not** part of the game and isn't reachable from `index.html`.

Don't scaffold systems that haven't been asked for yet — build the next milestone when the user asks for it, not preemptively. (Example: HUD's score/gold display is intentionally inert placeholder chrome, not a bug — no scoring system has been requested yet.)

## Architecture & conventions to preserve

- **Composition root**: [main.js](js/main.js) is the *only* place that touches the DOM and wires concrete dependencies together. Don't reach into `document` from elsewhere — pass dependencies in through constructors instead. `Game` needs `window`/`document` listeners (resize, visibilitychange) for its own lifecycle, but even those are registered *from* `main.js` calling public `Game` methods (`game.resize()`, `game.resumeFromBackground()`), not by `Game` reaching for the globals itself.
- **Config is data-only**: [Config.js](js/core/Config.js) is a frozen object containing constants only, no logic. Add new tunables there rather than hardcoding magic numbers inside systems — this has been retrofitted onto every entity that used to hardcode visual/physics tuning (Particles' spark/ring tuning, Drifter's path-shape and tentacle-animation constants, Sniper's charge-orb/warning-marker/bullet tuning all now live in `Config.particles` / `Config.enemy.drifter` / `Config.enemy.sniper` / `Config.enemy.sniper.bullet`), so match that pattern for new tunables rather than reintroducing inline literals.
- **Renderer is the seam**: [Renderer.js](js/core/Renderer.js) wraps the canvas 2D context and exposes a small, intentional surface of primitives (`clear`, `drawImage`, `drawText`, `strokePaths`, `fillStrokePaths`, `fillEllipse`, `strokeCircle`, `drawFlame`) in *virtual coordinates* — note `drawImage` takes an optional `alpha` (0–1) so scenes can fade blits in/out without ever touching `globalAlpha` themselves. Scenes and entities must never call `canvas.getContext('2d')` or touch the raw context — extend the Renderer's API instead, adding only the primitives a feature actually needs, and removing them again once their last caller is gone. The one standing exception is [Starfield.js](js/entities/Starfield.js)'s off-screen tile bake (`_bakeTile`, drawing directly via a throwaway `<canvas>`'s own 2D context) — acceptable because it's a one-time static-texture bake, not a draw to the shared display surface Renderer abstracts. This keeps the rendering backend swappable later (WebGL/PixiJS/etc.) without rewriting game systems.
- **Virtual coordinate system**: gameplay is authored against a fixed 540×960 (9:16) virtual resolution (`Config.virtual`). `Renderer.resize` derives one scale factor mapping virtual units to backing-store pixels (accounting for `devicePixelRatio`). Always express new positions/sizes/speeds in virtual units (e.g. virtual px/second for motion), never raw canvas pixels.
- **Scenes own `update(dt)` + `render()`**; `Game` owns *which scene is active*: `Game._tick` calls both on `this.scene` each frame, where `dt` is the elapsed time in seconds (so motion is frame-rate independent — always multiply speeds by `dt`, never apply a fixed per-frame step). Scene *transitions* are a plain constructor-injected callback — every scene takes `{ onContinue }` and calls it once it's done; `Game._start*` methods are what actually swap `this.scene`. Follow this same shape (inject a completion callback, let `Game` decide what runs next) for any future scene transition rather than having scenes import or construct each other.
- **Entities own `update(dt)` + `render(renderer)`** the same way scenes do, composed into whichever scene needs them (`Player`, `Bullets`, `HUD`, `Barrier`, `Starfield`, `WaveManager` are all composed into `GameplayScene`; `Portal`/`Starfield` into `PrologueScene`). `WaveManager` owns every enemy/projectile/particle-pool instance for the active level and batches enemy hull rendering by (type × hit-flash) into a handful of `fillStrokePaths` calls — see its class doc for the exact batching scheme — rather than each enemy drawing itself individually; only Drifter/Bouncer (whose geometry varies per-clone) render themselves directly.
- **Shared enemy-combat behavior lives in [EnemyCombat.js](js/entities/EnemyCombat.js)**, not a base class: `Enemy`, `SniperEnemy`, `DrifterEnemy` (and, partially, `BouncerEnemy`) have different constructor shapes, so the common pieces (`applyHit`, `tickDeathState`, `setState`, `stepEntryGlide`, `renderEngineFlame`, `renderEngineCore`) are plain functions taking the enemy instance as their first argument, each class opting into only what it needs. Follow this same shape — small shared functions over the file that owns the concept, not inheritance — for any future cross-enemy behavior; nothing in this codebase uses `extends`.
- **Small single-purpose modules under `js/core/`** hold generic, gameplay-agnostic helpers reused across entities/scenes, parallel to the input classes (`SwipeInput`/`TapInput`/`DragInput`): [animation.js](js/core/animation.js) (easing/flicker curves), [shapes.js](js/core/shapes.js) (parameterized point-geometry for the sci-fi corner-bracket/diamond chrome motif), [AudioPool.js](js/core/AudioPool.js) (lazy round-robin `Audio` pool — every repeated-SFX site in the game uses this now, not a hand-rolled pool), [textLayout.js](js/core/textLayout.js) (canvas word-wrap), [vectorMath.js](js/core/vectorMath.js) (`directionalVelocity` for straight-line projectile launches). Add new cross-cutting, non-gameplay-specific helpers here rather than duplicating them per file.
- **Input is gesture-level and scene-routed**: [SwipeInput.js](js/core/SwipeInput.js), [TapInput.js](js/core/TapInput.js), and [DragInput.js](js/core/DragInput.js) each wrap the Pointer Events API (one code path covers touch *and* mouse) and report normalized callbacks. `Game` owns one instance of each and forwards gestures to whichever scene is currently active via optional handlers (`scene.handleSwipeUp?.()`, `scene.handleTap?.(x, y)`, `scene.handlePointerDown/Move/Up?.()`) — scenes that don't care about a given gesture simply don't implement its handler. Extend this same optional-handler-on-the-active-scene shape for future gestures rather than wiring per-scene listeners. `DragInput` tracks a single active `pointerId` so a second touch during a drag can't hijack or prematurely end it.
- **Bake static repeating content to off-screen tiles**: [Starfield.js](js/entities/Starfield.js) (composed by both `GameplayScene` and `PrologueScene` — extracted into its own entity once both needed the same sky) bakes each parallax layer ONCE to a private off-screen `<canvas>` tile (`_bakeTile`), then every frame just translates and blits that tile twice via `Renderer.drawImage` (the standard two-copy seamless-scroll technique: one copy one tile-height above the other, so the wrap point is never visible). This keeps per-frame draw-call count flat and tiny regardless of star count — apply the same bake-once-blit-many approach to any future dense, static-relative-to-itself, repeating visual rather than redrawing every element every frame. `render`'s optional `alpha` lets each owning scene drive its own entrance fade without Starfield needing an opinion about *when* it should appear — reuse that shape (an `_age`-driven alpha passed in, not owned internally) for any future scene-entry/exit fade.
- **Full-screen, frame-free**: there is deliberately no device/phone-frame chrome — `.app` (the stage, `#game-stage`) is `width: 100%`, so on real phones (always narrower than the cap) it fills the device edge-to-edge. `max-width: var(--game-max-width)` is derived as `calc(100dvh * 9/16)` (the exact 9:16 proportion at whatever the viewport's height is, rather than a fixed pixel guess) and only ever engages on screens *wider* than that, capping and centering the play area so desktop/tablet users still see something that reads as "a phone screen" rather than a stretched-out rectangle. Its background matches the canvas's void color via the shared `--void` custom property (see `base/_reset.css` — must be kept in sync by hand with `Config.colors.void`, there's no build step to share the value), so any letterbox bars blend in invisibly. Don't reintroduce bezel/border/decorative-frame wrappers around the stage — the cap is a size limit, not a mockup chrome.
- **Avoid `100vw`/`100vh` on the stage**: they include the scrollbar gutter and can overshoot the visible viewport, creating a stray gap + scrollbar. `html`/`body` carry `overflow: hidden` and `.app` uses `width: 100%` / `height: 100dvh` instead — preserve this combo if you touch viewport sizing.
- **Letterboxing**: `Game._onResize` fits the virtual aspect ratio inside the available stage space without distortion — preserve this behavior when touching resize/scaling logic.
- **Audio playback must start inside the user-gesture handler**: `Game._startGameplay` calls `audio.play()` synchronously, reached via a direct callback chain from the tutorial's last hint tap (`handleTap` → `_advance` → `onContinue` → `_startGameplay`) — never after an `requestAnimationFrame`-driven animation, since that can run past the gesture's "user activation" window and cause the `play()` promise to reject. Any future scene that triggers sound on a gesture must do so immediately in the handler or a synchronous call chain from it, not after an animation "looks done".

## Style notes

- Each core file opens with a JSDoc-style block comment explaining *why* the file exists and what seam/responsibility it owns (not just what it does). Match this tone when adding new core files — explain rationale, not mechanics.
- No build tooling: code must run as-is via `<script type="module">`. Stick to ES module syntax that browsers support natively (no TypeScript, no JSX, no bundler-only features).
- CSS is layered (`base` → `layouts`, with a `components/` layer to be added as UI grows) and aggregated via `@import` in [main.css](css/main.css). Follow the existing BEM-ish naming (`.app__canvas`) and, for new UI components, give each its own `components/_*.css` file plus an `@import`. In practice almost all UI is canvas-drawn (HUD, menus, hints) — CSS only styles the page shell around the canvas.

## Running & verifying changes

Serve over HTTP — ES modules are blocked from `file://` URLs. With XAMPP/Apache running, open `http://localhost/space-shooter/`. There is no test suite or build step; verify visual/behavioral changes by loading the page in a browser (play through the prologue/tutorial/at least one full level, and check the responsive letterboxing by resizing the window).
